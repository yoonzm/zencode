# ZenCode

Tauri 2 + Rust desktop application, retaining the React / TypeScript / Tailwind 4 interface from [yoonzm/zencode-ui](https://github.com/yoonzm/zencode-ui), initial baseline `33c33acb1e557d00d4016fcb9d677cd44ff0ed88`, with UI components synchronized through `e6c15bd`. Desktop service wiring and fixes are retained; prototype simulation controls are excluded.

## Development

The macOS build requires macOS 13.3+ to match the existing UI’s Safari 16.4 CSS target.

Install Node.js 24, stable Rust, Git, and [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/). Install and log into the official Codex CLI separately (`codex login`). ZenCode uses the CLI's existing account and default model; the composer and settings load models and supported reasoning efforts from the local app-server model/list catalog. Refresh after changing CLI accounts. Model and effort selections are passed to task and verification turns; changes apply on the next task start/resume. Catalog entries can be cached by Codex; actual execution reports access errors.

```
npm ci
npm run typecheck
npm test
npm start
npm run package
```

`npm test` builds/tests the Rust core without native WebView dependencies. Full desktop builds require platform libraries. `npm run build` uses Vite and Tailwind CSS to produce `dist` with external scripts and styles for Tauri CSP. UI primitives use Radix/shadcn, HeroUI, Magic UI, Motion, lucide-react, Zustand and cmdk. `npm run dev` starts the browser preview; desktop service calls require Tauri.

## Runtime

- Deleting a task stops its execution and removes its independent local workspace, including local branches and uncommitted changes. Workspace cleanup failures keep the task available for retry. ZenTao tasks and remote Git branches are unaffected.
- Native OS window decorations provide the window controls. Platform appearance and shortcut labels follow the actual runtime platform; prototype platform overrides are no longer restored.
- Closing the main window hides ZenCode to the system tray and keeps background tasks running. Click the tray icon, choose “打开 ZenCode”, or launch ZenCode again to restore the window. Choose “退出” from the tray menu to quit and stop background workers; updater restarts still use the normal shutdown path.
- ZenTao and GitLab each offer an opt-in **Advanced > Skip certificate verification** setting (off by default). It applies only to that service's API client, including authentication, synchronization, attachments and MR API requests. Certificate failures reveal the setting; successful tests identify when verification was skipped. Git push retains the local Git TLS configuration. No global TLS or Git settings are changed.
- Rust performs HTTP requests, Git operations and the Codex app-server JSON-RPC protocol. There is no bundled Node/Electron server.
- Windows credentials use Credential Manager; macOS uses Keychain through keyring. Credentials are never saved in renderer localStorage. Linux credential persistence is explicitly unsupported in this release.
- Task state is saved in the OS application data directory, with a backup on replacement. A damaged state file is reported, not silently reset.
- ZenTao REST v1 (`/api.php/v1`) uses token or password authentication. Synchronization only reads bugs, stories and task details for products with a configured repository mapping. Within those products, the synchronization scope selects either tasks assigned to the configured account or all assignees. The full product catalog remains available for configuring mappings.
- Automatic ZenTao synchronization defaults to every 5 minutes, including older saved configurations without this field. Settings allow disabling it or choosing 1?1440 minutes. It continues while the window is in the background, skips setup, avoids overlapping requests and keeps the current list on background failures. Failed attempts wait for the next configured interval.
- Automatic execution after synchronization defaults to enabled, including older configurations. Only newly imported tasks with repository mappings enter the existing concurrency queue; existing tasks are not restarted. Disable it in ZenTao settings to leave new tasks idle. Manual and scheduled sync follow the same rule, including locally deleted tasks imported again. Execution still requires human review before MR submission.
- Deleting a task removes its local record after stopping any active or queued execution; it does not modify ZenTao. The next synchronization imports it with a fresh run. Existing worktrees and Git branches remain on disk for recovery but are not reused by the imported task.
- Repository mappings select GitLab projects and target branches from the API, with pagination and refresh/error feedback. Local checkout paths are no longer required. Each new task execution clones the selected target branch into an isolated directory under application data and creates its own branch. Pause/resume retains the existing checkout and history. Clone and push use the local Git SSH/credential configuration; the API token is not written into clone URLs.
- Product, repository and branch selectors support search and a shared refresh action. A product can map to several repositories with individual branches, role labels and test commands. Synchronization creates a separate local task/run per repository, each with its own review and MR. Existing single-repository settings migrate on load; existing runs and task links are retained when the repository is unchanged. Reordering mappings does not restart runs.
- AI matching uses the configured Codex CLI to compare actual ZenTao BUGs/stories with GitLab commits, MRs and project events. Candidate products are deduplicated from all pages of the current authenticated ZenTao user's assigned BUGs/stories via `/user?fields=bug|story&type=assignedTo`; assignment age is not restricted. The token identity must match the configured account when supplied. Only those product details are fetched; unsupported workbench responses fail explicitly without falling back to the full catalog. Candidate repositories come from the GitLab token user's past-90-day events and authored/assigned/reviewed MRs, with pagination and no global repository scan. Subsequent evidence enrichment is scoped to these candidates and can include other contributors. It reads up to 100 BUGs and 100 stories per product (descending ID, with detail enrichment for the ten newest of each), and up to 100 entries per repository/source from the past 90 days, including commits across branches. Number references, business content, participants, branch names and dates inform suggestions; bare numeric IDs or activity alone are insufficient. Every accepted suggestion must cite real task and repository records belonging to that pair, and the dialog displays their actual excerpts. Confidence is a model estimate, not a verified probability. Sampling limits and partial API failures appear in the dialog. Matching has no product/repository count cutoff or local prompt-size cutoff. Collection uses per-request timeouts instead of a fixed total deadline; large catalogs can take longer and remain subject to the model context capacity. Per-source history sampling still applies. Credentials are excluded from the prompt. Applying suggestions edits only the draft mapping, with GitLab's actual default branch. Live model matching and native dropdown interactions still require desktop validation.
- Codex uses `app-server --listen stdio://`, thread start/resume, turn start/steer/interrupt, message streaming and command/file approval responses. “Always” currently means the current Codex session. Pause interrupts the current turn; resume creates a new turn in the same thread, not an OS process freeze.
- Review shows a real Git diff, including new files. Clicking MR stages, commits and pushes that isolated branch, then creates/reuses the MR and marks the local run complete. Git push uses the user's configured Git credential helper/SSH, independently of the API PAT. Origin is verified against the configured GitLab project before push.
- Before MR submission, all effective `origin` push URLs are checked against the project's GitLab-provided SSH or HTTP clone URL. SSH and HTTP API ports are independent; a separate or additional `pushurl` must still match the project.
- MR failure remains reviewable. Successful MR submission completes the local run without writing comments, links, status or fix versions to ZenTao. ZenTao status remains read-only and comes from synchronization. Legacy pending runs retain their MR open/copy actions and can finish submission without creating another MR.

## Installers and validation limits

The `Desktop installers` GitHub Actions workflow builds Windows x64 NSIS `.exe`, macOS Apple Silicon `.dmg`, and macOS Intel `.dmg`. Artifacts are private workflow downloads, not public releases. Signing/notarization credentials are not configured.

This is an implementation in validation, not a claim of complete production readiness. Live ZenTao/GitLab integration, interactive Windows/macOS flows, and credential-vault roundtrips still require those systems/accounts. Attachment downloads require a binary REST v1 file response (up to 50 MB); incompatible preview/JSON responses report an error. Legacy ZenTao APIs are not supported. MR submission does not write to ZenTao. Unsupported Codex interaction requests fail explicitly. No external test tenant is included, and no successful remote mutation is fabricated. See test output and workflow artifacts for verified results.

## Versioned releases

Ordinary branch pushes build private CI artifacts only. After updating package/Tauri versions consistently, push a `vX.Y.Z` tag to build all three installers and publish a Release only after their tests and platform checks succeed. Only the release job requests contents write permission; repository access settings remain unchanged.

To publish an already verified build, manually run **Publish verified installers** with its successful Desktop installers run ID, exact 40-character commit SHA and matching version tag. This reuses the original artifacts. Conflicting tags or existing releases are rejected; assets are never overwritten. Upload failures leave a draft for inspection. Installer checksums are included in SHA256SUMS.txt. Keep validation limitations in the release notes current before future versions.

Tag pushes now run a lightweight build-decision check before allocating the Windows/macOS matrix. A tag with an existing same-SHA release (including an upload-complete draft during publication) skips the matrix and automatic release job only when its recorded Desktop installers run succeeded, all three platform jobs passed, all three source artifacts remain available, and the three versioned installers plus checksum manifest are uploaded and hashed. A mismatched SHA or incomplete/expired/unverified artifact set fails the check for inspection instead of silently reusing or overwriting it. New tags without a release, branch pushes and manual builds still build normally. This avoids re-packaging after publishing existing installers; the small decision job may still consume a runner minute. Test locally with `python3 -m unittest discover -s test -p '*_test.py'`.

## Product verification

Product mappings support an enabled switch and free-form verification instructions. After code changes and self-checks, Codex prepares a separate test plan and executes it, automatically proceeding to verification. The verification tab shows the plan, reported evidence and actual command logs; reviewable tasks can run verification again. Missing/disabled instructions, skipped plans, interruptions or invalid reports remain unverified. Reports require nonempty steps with evidence before showing passed; results are Codex-reported and need human review. MR descriptions include the report, and anything other than passed forces a Draft MR. Existing repository role/test-command values remain compatible although the simplified mapping editor no longer edits them.

The mapping editor's **AI draft** clones the currently selected repository branches into an isolated temporary directory and asks Codex to read their actual documentation, scripts and test configuration. The generated instructions are previewed and replace the current draft only when explicitly applied. **Trial run** clones those same target branches and executes the current unsaved instructions through Codex, honoring its configured sandbox, command approvals and automatic test-plan execution. It shows source commits, command logs and a structured result; cancellation, missing environments and invalid reports cannot produce a successful result. Trial runs do not create task records or MRs. Only one mapping tool runs at a time, with a 30-minute limit; closing its dialog cancels it. Sessions are closed and temporary directories are cleaned up when the operation ends. Cleanup failures are shown in the logs. Synthetic recording controls remain excluded. Live model and target-environment validation still depends on the configured CLI tools and environment; regression tests use a real Git HTTP clone and a controlled app-server fixture.

## Application updates

The sidebar and About page check actual GitHub Releases in `yoonzm/zencode`. Stable selects only newer stable versions; beta selects the newest eligible stable or beta version. Versions use semantic ordering and never downgrade automatically. Older releases without updater manifests are skipped. Checks run four seconds after preferences load and every six hours while enabled. Download and installation are explicit actions. Network errors are shown in About; background failures do not repeatedly toast.

The Rust updater downloads immutable `stable.json` / `beta.json` release assets and verifies update signatures before installation. The currently installed version comes from Tauri. Download bytes are held only in the current process, so restarting before installation requires downloading again. Only preferences are persisted; a stale frontend `ready` state is never trusted. Update endpoints use public HTTPS and do not reuse ZenTao/GitLab credentials or their TLS bypass settings.

Before installation the backend serializes with synchronization and MR submission, blocks new task operations, requests interruption of running Codex turns, cancels queued workers, and waits up to 45 seconds for workers to finish. Failure to pause or save aborts installation. Waiting approval/verification-plan tasks must be handled first. A persisted version-bound recovery list resumes only update-paused running/queued tasks after the target version launches. Manually paused tasks stay paused; installer failure leaves tasks available for manual continuation. Recovery resumes the saved Codex thread/worktree, not a frozen OS process. External command side effects are not rolled back.

### One-time release configuration

1. Generate a Tauri updater signing key outside this repository (`npm run tauri -- signer generate -w <private-key-path>`). Keep a secure backup; never commit the private key.
2. Set GitHub Actions repository variable `ZENCODE_UPDATER_PUBLIC_KEY` to the public key file's **contents**.
3. Set repository secret `TAURI_SIGNING_PRIVATE_KEY` to the private key file's contents and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` to its password if set.
4. Ensure `https://api.github.com/repos/yoonzm/zencode/releases` and release assets are publicly readable. A private source repository needs a separately configured public distribution repository or authenticated update service; this implementation does not embed a GitHub token or change repository visibility.
5. Keep `package.json`, `package-lock.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, and `src-tauri/tauri.conf.json` versions consistent. Publish `vX.Y.Z` for stable or `vX.Y.Z-beta.N` for beta.

The desktop workflow embeds the public key, creates signed NSIS/macOS updater bundles, and retains the normal DMG installers. The release workflow requires all three platforms, signatures and checksums before publishing the draft; it attaches an immutable channel manifest to each release. Beta releases are marked prerelease. Manual publication of an old installer-only build fails explicitly because it has no signed updater artifacts. Branch builds can still run without signing credentials, but About reports that automatic updating is unavailable in such builds. Updater signatures are separate from Windows Authenticode/macOS signing and notarization.

The first updater-capable version must be installed manually. Validate an actual old-to-new upgrade on Windows x64 and both macOS architectures before distributing broadly; automated tests do not replace this installer roundtrip. No signing credentials, remote configuration or release publication are performed by a local code change.

## Manual requirements

UI synchronized through `zencode-ui` commit `df549fe`: stop/continue controls retain the task workspace and thread; messages submitted during a running turn queue for the next turn. Pending messages survive stop/restart. Existing persisted `paused` tasks display as stopped. The task menu and diff rows open the actual workspace or file in VS Code (requires its registered URL handler), or the system file manager. While viewing a task, returning to the window or the five-second refresh detects changes made outside an active Codex run and marks changed files as manual edits. Concurrent edits during an active run cannot be reliably attributed to a person.

The task list and command palette offer **新增需求**: paste source text, ask the configured Codex CLI to organize it, review/edit the candidates, then import. Organization is read-only with tools disabled and a three-minute timeout; errors preserve the input. Only source text and configured product names are sent to the model. Generated content requires review.

Import persists the entire batch atomically, creates one idle task per mapped repository, and retains the original source. Manual tasks use N-prefixed local numbers, survive ZenTao synchronization, and never auto-run on import or link to ZenTao. Deletion cannot restore them through synchronization. They use the existing execution, verification and MR workflow; MR descriptions identify the manual origin. Local fixture tests cover organization and persistence; live model and native desktop validation remain environment-dependent.

## Feishu notifications

UI synchronized through `e6c15bd`. Notification settings support opt-in Feishu/Lark custom-bot delivery, signed requests, an explicit test button and message previews. Webhook URLs and signing secrets use the system credential vault. Background runtime transitions send approval/verification-plan requests, failures, verification failures, review-ready results and MR completion independently of desktop notification preferences. Streaming updates do not repeat notifications. Delivery errors are reported without exposing webhook credentials; delivery has a 15-second timeout and no automatic retry or offline replay.

Messages contain task number/title, product, changed-file count and MR branch/link when applicable; requirement bodies, code, commands and model output are excluded. Return to ZenCode by task number: app deep links and personal @ mentions are not implemented. Tests do not send to live groups; validate actual delivery with the settings test button after configuring a bot. Signing follows the [Feishu custom bot guide](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot).

Browser verification instructions require Playwright in headless mode with a fresh isolated browser context for task verification, re-verification, resumed sessions and mapping trials/drafts. They prohibit Computer Use, user-browser profiles/cookies and attaching to existing browsers or CDP endpoints. Missing tools or test credentials must be reported as unverified, never worked around using a personal browser. This is an agent instruction constraint, not an OS-level browser access sandbox.

Browser verification uses a shared Node runner in the application data directory (verification-runtime), pinning Playwright 1.58.2 and Chromium. First use installs them; subsequent tasks and worktrees reuse them. An exclusive cross-process lock prevents concurrent installation, and every use checks a real headless launch. Run task .cjs scripts through the runner to resolve require("playwright") and the browser cache. Planning does not install anything. Installation or launch failures remain unverified. After forced termination, inspect install.lock and confirm the installer and its children have stopped before removing the abandoned lock. Version changes or deleted caches require installation again. Browser contexts and credentials are isolated per task.

Task deletion keeps the confirmation open with real stage feedback until the task has stopped and its removal is saved. Workspaces are renamed into the application-owned pending-delete directory; recursive removal runs on a blocking worker after the task leaves the list. A durable pendingDeletes journal restores an uncommitted move after a crash, and resumes committed cleanup on application load. Failed cleanup is retried every 30 seconds and on restart. Deleting tasks reject duplicate deletion, start, MR, and conflicting cleanup operations; the global task mutation lock is released while waiting for the worker to stop. Progress events and cleanup logs include elapsed milliseconds. Physical cleanup does not touch the shared verification-runtime directory.
